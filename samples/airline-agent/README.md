# Transport — Airline Agent

A stateful, event-driven airline operations pipeline built on the Event Rule Agent pattern. It
shows how Flink and an IBM Decision Intelligence rule archive can manage the events generated by an
airline system: **flight events** (flight open, flight delayed…), **passenger events** (check-in,
cancel check-in…) and **catering events** (meal counts) are correlated per flight and turned into
flight, passenger and catering notifications.

It also demonstrates two advanced Agent features:

- **Reference-data enrichment** — `FLIGHTOPEN` events are enriched with aircraft specifications,
  passenger manifests, and catering data from CSV reference files before the rules run. The same
  way, `PassengerNotification` events are enriched with passenger contact details before being
  pushed to Kafka. By default this uses the CSV-based enrichment of [`agents.json`](agents.json),
  which runs on both the DataStream and the PTF runtimes. The alternative descriptor
  [`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) shows the same enrichment
  written as Flink SQL scripts, which is only available when the DataStream runtime is used.
- **Scheduling** — when a flight is opened, a rule asks the Agent to wake up 48 hours before
  departure and notify passengers that check-in is open.

## 1. Subscriptions and operations

The Agent consumes three Kafka topics plus the internal `Schedule` event. Each event type is routed
to its own Decision Intelligence operation. In every operation the entity (the `Flight`) is passed
in as `flight`, and the matching history is passed in as a `past…Events` list.

| Event type | Topic | Operation | Current event field | History field | Horizon | Pre-enrichment |
|---|---|---|---|---|---|---|
| `FlightEvent` | `agent-flight-events` | `ProcessFlightEvent` | `flightEvent` | `pastFlightEvents` | time — 96 h | ✓ CSV (default) or SQL — see [§5](#5-enrichment) |
| `PassengerEvent` | `agent-passenger-events` | `ProcessPassengerEvent` | `passengerEvent` | `pastPassengerEvents` | time — 96 h | — |
| `CateringEvent` | `agent-catering-events` | `ProcessCateringEvent` | `cateringEvent` | `pastCateringEvents` | hybrid — last 100 events or 96 h | — |
| `Schedule` | *none (generated by the Agent)* | `ProcessSchedule` | `schedule` | `pastFlightEvents` | — | — |

Every operation can return:

- `flightNotifications` and `passengerNotifications` (outbound
  events, depending on the operation — see [`agents.json`](agents.json)),
- `scheduleRequests` (`scheduleRequestsField`), used to register timers.

The `Schedule` subscription has no topic and no horizon: the events are produced by the Agent when a
timer registered through a `ScheduleRequest` fires. See
[§7.4 Scheduling](../../docs/AGENT_PATTERN_DESIGN.md#74-scheduling) for the semantics.

The `FlightEvent` subscription declares an `enrichment`: raw events from `agent-flight-events` are
completed with CSV reference data before reaching the rule engine. The alternative
`agents-with-sql-enrichment.json` uses a Flink SQL script instead (DataStream runtime only). See
[§5 Enrichment](#5-enrichment).

The passenger topic is declared with `"idleness": "30s"` in the top-level `topics` of [`agents.json`](agents.json) so
that a quiet passenger topic does not hold back the event-time watermark and delay schedules.

The ruleset also declares the archive control topic `agent-airline-archive-control`, used for
zero-downtime archive reloads.

See [`../../docs/AGENT_PATTERN_DESIGN.md`](../../docs/AGENT_PATTERN_DESIGN.md) for the generic
rule signature and the full descriptor field reference.

## 2. Event shapes

All timestamps are ISO-8601 UTC strings. Every event must carry the `flightNumber`, which is the
entity key. The full data model is in the BOM of the
[decision project](di-project/AirlineDecisionService.zip).

### Flight event — `agent-flight-events`

| Field | Description |
|---|---|
| `timestamp` | Event time |
| `flightNumber` | Entity key |
| `type` | `FLIGHTOPEN`, `FLIGHTDELAYED`, `FLIGHTCANCELLED`, `FLIGHTCLOSE`, `FLIGHTINFO`, `PASSENGERADDED`, `PASSENGERMODIFIED`, `PASSENGERREMOVED` |
| `flight` | The flight data (see below). `FLIGHTOPEN` carries the full flight; other events only the changed fields (for example `expectedDate` for `FLIGHTDELAYED`) |

The rules currently act on `FLIGHTOPEN` and `FLIGHTDELAYED`. Other types are stored in the event
history and can be used to advance event time.

```json
{
  "timestamp": "2026-10-01T20:29:16Z",
  "flightNumber": "EY082",
  "type": "FLIGHTOPEN",
  "flight": {
    "flightNumber": "EY082",
    "aircraftId": "AF-343-TY",
    "aircraftType": "A380",
    "date": "2026-10-15T20:29:16Z",
    "expectedDate": "2026-10-15T20:29:16Z",
    "origin": "CDG",
    "destination": "LHR",
    "duration": "PT1H",
    "cateringInformation": {
      "economyTotalMealCount": 10,
      "businessTotalMealCount": 10,
      "firstTotalMealCount": 10
    },
    "passengers": [
      {
        "passengerId": "JS",
        "name": "John Smith",
        "birthdate": "1980-10-19T20:29:16Z",
        "citizenship": "USA",
        "residenceCountry": "USA",
        "loyaltyStatus": "Gold",
        "check-inStatus": "Pending",
        "travelClass": "Economy"
      }
    ]
  }
}
```

`Flight` enumerations: `loyaltyStatus` is `Gold`, `Silver` or `Platinum`; `check-inStatus` is
`Pending`, `CheckedIn` or `Cancelled`; `travelClass` is `Economy`, `Business` or `First`. The
optional `checkinCounter` object (`economyCheckinCounter`, `businessCheckinCounter`,
`firstCheckinCounter`) holds the number of checked-in passengers per class.

### Passenger event — `agent-passenger-events`

```json
{
  "timestamp": "2026-10-14T13:30:00Z",
  "flightNumber": "AF099",
  "passengerId": "LW",
  "type": "CHECKIN"
}
```

`type` is `CHECKIN`, `CANCELCHECKIN` or `NOSHOW`. `passengerId` must match a passenger of the
flight.

### Catering event — `agent-catering-events`

```json
{
  "timestamp": "2026-10-13T13:30:00Z",
  "flightNumber": "AF021",
  "cateringInformation": {
    "economyTotalMealCount": 5,
    "businessTotalMealCount": 5,
    "firstTotalMealCount": 5
  }
}
```

### Schedule event (internal)

Produced by the Agent when a `ScheduleRequest` fires. It is never sent to Kafka.

| Field | Description |
|---|---|
| `timestamp` | The timer timestamp |
| `id` | `id` of the `ScheduleRequest` that fired (for example `CHECK-IN-OPEN`) |
| `description` | `description` of the `ScheduleRequest` |

## 3. Output topics

| Event type | Topic | When |
|---|---|---|
| `FlightNotification` | `agent-flight-notifications` | A flight-level notification is raised (delay, possible cancellation, check-in open, meal shortage…) |
| `PassengerNotification` | `agent-passenger-notifications` | A notification addressed to one passenger (for example check-in open) |
| `entity-changelog` | `agent-flight-entity-changelog` | Flight entity state updated (side-output, every cycle) |
| `agent-error` | `agent-airline-errors` | Rule engine or processing errors |

The top-level `topics` of `agents.json` expose the inbound topics in the dashboard; the outbound topics
(flight notification, passenger notification, error and changelog) are derived from the agent's `outputs`
and `stateConfig.changeLogTopic`.

### Flight notification output shape

| Field | Description |
|---|---|
| `timestamp` | Time the notification was raised |
| `flightNumber` | Flight concerned |
| `type` | `Cancelled`, `CheckInOpen`, `Closed`, `Delayed`, `Information`, `MealShortage`, `MealShortageCleared` |
| `message` | Human-readable text |

```json
{
  "timestamp": "2026-10-15T13:50:00Z",
  "flightNumber": "AF077",
  "type": "Information",
  "message": "Burst of Delay Event indicating a potential flight cancellation"
}
```

### Passenger notification output shape

| Field | Description |
|---|---|
| `timestamp` | Time the notification was raised |
| `flightNumber` | Flight concerned |
| `passengerNumber` | `passengerId` of the addressee |
| `message` | Human-readable text |

```json
{
  "timestamp": "2026-10-13T20:29:16Z",
  "flightNumber": "EY082",
  "passengerNumber": "JS",
  "message": "Checking for Flight: EY082 is open. Please check-in online"
}
```

### Entity changelog

When `stateConfig.changeLogTopic` is set (this agent uses `agent-flight-entity-changelog`), a
side-output record is emitted to that topic whenever the rule engine returns an updated `Flight`
entity. Each record has the form:

```json
{
  "entityId":   "AF021",
  "entityType": "Flight",
  "timestamp":  1750000000000,
  "entity":     { "flightNumber": "AF021", "shortMealSituation": true, ["..."] }
}
```

## 4. Decision rules

All rules live in the Decision Intelligence archive (`AirlineDecisionService`). The decision project
has one rule project per operation (see [§1](#1-subscriptions-and-operations)) plus a shared data
model, `AirlineDataModel`. The rules are described in detail in the documents under
[`di-project/docs/`](di-project/docs/):

| Document | Content |
|---|---|
| [`ontology.md`](di-project/docs/ontology.md) | The business object model: concepts, properties, enumerations and helper functions used by the rules |
| [`event-processing.md`](di-project/docs/event-processing.md) | The four operations, their ruleflows, and every rule package and rule (when it fires, what it does) |
| [`situations.md`](di-project/docs/situations.md) | The business situations the rules detect: delay, possible cancellation, meal shortage (thresholds and state machine), early check-in, check-in opening |

In short, the rules do the following:

| Operation | What the rules do |
|---|---|
| `ProcessFlightEvent` | Initialize the flight on `FLIGHTOPEN` and schedule the `CHECK-IN-OPEN` callback 48 h before departure; store the new expected date and notify on `FLIGHTDELAYED` (at most once per 30 minutes, with a possible-cancellation warning on a burst of delays) |
| `ProcessPassengerEvent` | Check in or cancel the check-in of the passenger, warn on a check-in more than 48 h before departure, and raise or clear the meal shortage |
| `ProcessCateringEvent` | Store the received meal counts on the flight, then raise or clear the meal shortage |
| `ProcessSchedule` | On `CHECK-IN-OPEN`, raise a flight notification and notify every passenger of the flight |

The meal shortage is the only stateful situation: the flight keeps a `shortMealSituation` flag, so a
notification is raised only when the situation changes, whichever event (passenger or catering)
triggers it.

### Rule examples

Rules are written in the Decision Intelligence business language. Three representative ones:

```
// Flight Initialization Rule
if
    the type of 'the flight event' is FLIGHT OPEN
then
    // initialize the entity
    set the flight of 'the result' to the validated flight from the flight of 'the flight event' ;

    // post a schedule to trigger a check-in open event 48h before departure
    add a new Schedule Request where
        the id is "CHECK-IN-OPEN" ,
        the status is "START",
        the description is "Trigger check-in open event 48h before flight" ,
        the timepoint is the date of the flight of 'the flight event' - 48 hours
    to the schedule requests of 'the result' ;
```

```
// Flight Delayed Notification Rule
if
    the type of 'the flight event' is FLIGHT DELAYED
  and
    // avoid sending too much notifications
    there is no Flight Event in 'the past flight events'
        where the type of this Flight Event is FLIGHT DELAYED
        and this Flight Event is within 30 minutes before now ,
then
    add a new Flight Notification where
        the flight number is the flight number of 'the flight event' ,
        the timestamp is now ,
        the message is `Flight as being delayed. new expected time: { the expected date of the flight of 'the flight event' }` to the flight notifications of 'the result' ;
```

```
// Detect Short Meal Situation (catering events)
if
    'the flight' is not in short meal situation
    and it is not true that the catering situation for 'the flight' is good
then
    'the flight' gets short meal situation ;
    set the short meal situation start date of 'the flight' to now;
    define 'the notification' as a new Flight Notification where
      the timestamp is now ,
      the type is Meal Shortage ,
      the message is `Meal shortage situation. Available meals: {the report of the catering information of 'the flight'}, Passenger information: {the passenger information of 'the flight' }` ,
      the flight number is the flight number of 'the flight';
    add 'the notification' to the flight notifications of 'the result' ;
```

## 5. Enrichment

Enrichment can be applied at two points in the pipeline:

* **Inbound** — before the rule engine, to augment raw Kafka events with reference data.
* **Outbound** — after the rule engine, to enrich generated notification events before they reach
  the Kafka sink.

This sample ships two descriptors that implement the same enrichment with the two mechanisms
described in [§7.5 of the design guide](../../docs/AGENT_PATTERN_DESIGN.md#75-enrichment-mechanisms):

| Descriptor | Mechanism | Runtimes |
|---|---|---|
| [`agents.json`](agents.json) (**default**) | **CSV-based enrichment** — `references` + `enrichment` steps | DataStream and PTF |
| [`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) | **SQL-based enrichment** — `sqlEnrichment` Flink SQL scripts | **DataStream runtime only** |

The two files differ only by the `sqlEnrichment` blocks added on the `FlightEvent` subscription
and on the `PassengerNotification` output. On the DataStream runtime `sqlEnrichment` takes
precedence over `enrichment` when both are declared, so `agents-with-sql-enrichment.json` runs the
SQL scripts there; on the PTF runtime `sqlEnrichment` is ignored (with a warning) and the CSV-based
`enrichment` is applied.

---

### 5a. Default: CSV-based enrichment

[`agents.json`](agents.json) declares the four CSV files once, as agent-level `references`, and
each subscription or output lists lookup `enrichment` steps. See
[§7.6 Reference-Data Enrichment](../../docs/AGENT_PATTERN_DESIGN.md#76-reference-data-enrichment)
for the full syntax. No schema, SQL script or Table API is needed, so this works on both the
DataStream and the PTF runtimes (including Confluent Cloud, where the CSV files must be bundled in
the UDF JAR).

```json
"references": [
  { "name": "flights",    "type": "csv", "file": "samples/airline-agent/enrichment/flights.csv" },
  { "name": "passengers", "type": "csv", "file": "samples/airline-agent/enrichment/passengers.csv" },
  { "name": "catering",   "type": "csv", "file": "samples/airline-agent/enrichment/catering.csv" },
  { "name": "roster",     "type": "csv", "file": "samples/airline-agent/enrichment/flight_passengers.csv" }
]
```

**Inbound — `FlightEvent`.** Only `FLIGHTOPEN` events are enriched (each step has a `when` filter);
the other event types pass through unchanged. Four steps rebuild the full flight record the rules
expect:

| Step | Reference | Key | Written into | Fields |
|---|---|---|---|---|
| 1 | `flights` | `flightNumber` | `$.flight` | `flightNumber`, `aircraftId`, `aircraftType`, `date`, `origin`, `destination`, `duration` |
| 2 | `catering` | `flightNumber` | `$.flight.cateringInformation` | `economyTotalMealCount`, `businessTotalMealCount`, `firstTotalMealCount` |
| 3 | `roster` | `flightNumber` | `$.flight.passengers` (`cardinality: many`) | `passengerId`, `check-inStatus` (renamed `checkInStatus`), `travelClass` |
| 4 | `passengers` | `passengerId` | `$.flight.passengers[*]` | `name`, `birthdate`, `citizenship`, `residenceCountry`, `loyaltyStatus` |

Step 4 runs after step 3 because it fills the elements of the array step 3 creates; the order is
resolved automatically.

**Outbound — `PassengerNotification`.** The `passengers` reference is joined on `passengerNumber`
and `name`, `loyaltyStatus`, `email`, `phone` and `contactPreference` are merged into the
notification payload (`"into": "$"`) before it is written to Kafka. A passenger missing from the
registry still gets the notification, without the contact fields.

---

### 5b. Alternative: SQL-based enrichment

> **DataStream runtime only.** SQL enrichment needs the Flink Table API; the PTF runtime ignores
> `sqlEnrichment`. Use [`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) with
> the default runtime (see [§6](#6-running-this-use-case)).

[`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) illustrates the same
enrichment written as Flink SQL scripts. Both directions share the same three-column output view
contract (`timestamp`, `entity_id`, `payload_json`) and the same SQL runtime
(`SqlEnrichmentRunner`).

#### Inbound enrichment — `FlightEvent`

The `FlightEvent` subscription uses [Flink SQL enrichment](../../docs/AGENT_PATTERN_DESIGN.md#77-sql-based-enrichment)
to augment raw events before the rule engine sees them.

##### What is enriched

Only `FLIGHTOPEN` events are enriched. All other event types (`FLIGHTDELAYED`, `FLIGHTINFO`, …)
pass through unchanged using the `raw_payload` column.

A `FLIGHTOPEN` event arrives from Kafka carrying only the flight number and a minimal `flight`
object. The SQL script joins it against four CSV reference tables and rebuilds the payload with
the full flight record the rules expect:

| Reference file | Content | Fields added to `flight` |
|---|---|---|
| [`enrichment/flights.csv`](enrichment/flights.csv) | Aircraft specs and route per flight | `aircraftId`, `aircraftType`, `date`, `origin`, `destination`, `duration` |
| [`enrichment/passengers.csv`](enrichment/passengers.csv) | Global passenger registry | identity fields per passenger (`name`, `birthdate`, `citizenship`, …) |
| [`enrichment/flight_passengers.csv`](enrichment/flight_passengers.csv) | Flight–passenger join (one row per flight/passenger pair) | `check-inStatus`, `travelClass` |
| [`enrichment/catering.csv`](enrichment/catering.csv) | Meal counts per flight | `cateringInformation` (`economyTotalMealCount`, …) |

The resulting `FLIGHTOPEN` payload matches the full shape documented in [§2](#2-event-shapes)
exactly as if the producer had sent those fields directly.

##### Files

| File | Purpose |
|---|---|
| [`enrichment/enrich_flight_events.sql`](enrichment/enrich_flight_events.sql) | SQL script: DDL for the four reference tables, an intermediate `passengers_per_flight` aggregation view, and the final `enriched_flight_events` output view |
| [`schemas/flight-event.schema.json`](schemas/flight-event.schema.json) | JSON Schema for `agent-flight-events` — required by the SQL enrichment pipeline to derive Flink Table column types |
| [`enrichment/flights.csv`](enrichment/flights.csv) | Aircraft specs and route |
| [`enrichment/passengers.csv`](enrichment/passengers.csv) | Global passenger registry |
| [`enrichment/flight_passengers.csv`](enrichment/flight_passengers.csv) | Per-flight passenger list |
| [`enrichment/catering.csv`](enrichment/catering.csv) | Per-flight meal counts |

##### How the pipeline is declared

In [`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) the `FlightEvent`
subscription carries `sqlEnrichment` next to the CSV-based `enrichment` of the default descriptor
(which the DataStream runtime then ignores):

```json
{
  "eventType": "FlightEvent",
  "topic": "agent-flight-events",
  "operation": "ProcessFlightEvent",
  "horizon": { "type": "time", "timeLimit": "96h" },
  "sqlEnrichment": {
    "sqlFile":        "samples/airline-agent/enrichment/enrich_flight_events.sql",
    "inputViewName":  "raw_flight_events",
    "outputViewName": "enriched_flight_events"
  }
}
```

The top-level `topics[]` entry for `agent-flight-events` declares the schema path, which is
required for SQL enrichment:

```json
{
  "name":   "agent-flight-events",
  "type":   "FlightEvent",
  "label":  "Flight Events",
  "schema": "samples/airline-agent/schemas/flight-event.schema.json"
}
```

##### Output view contract

The final view `enriched_flight_events` projects the three columns required by the enrichment
pipeline:

| Column | Value |
|---|---|
| `timestamp` | `r.timestamp` (ISO-8601 string from the raw event) |
| `entity_id` | `r.flightNumber` |
| `payload_json` | Full enriched JSON for `FLIGHTOPEN`; `raw_payload` for all other types |

---

#### Outbound enrichment — `PassengerNotification`

The `PassengerNotification` output uses SQL post-enrichment to inject passenger contact details
into each notification before it is written to Kafka.  The rule engine only produces the minimal
notification payload (`timestamp`, `flightNumber`, `passengerNumber`, `message`); the SQL layer
adds the fields needed to actually deliver the message.

##### What is enriched

Every `PassengerNotification` event is joined against `passengers.csv` on `passengerNumber` and
the following fields are appended to the payload:

| Field | Source | Description |
|---|---|---|
| `name` | `passengers.csv` | Passenger full name |
| `loyaltyStatus` | `passengers.csv` | Loyalty tier (`Gold`, `Silver`, …) |
| `email` | `passengers.csv` | Email address |
| `phone` | `passengers.csv` | Phone number |
| `contactPreference` | `passengers.csv` | Preferred channel (`SMS`, `EMAIL`, `PHONE`, `WHATSAPP`) |

##### Files

| File | Purpose |
|---|---|
| [`enrichment/enrich_passenger_notifications.sql`](enrichment/enrich_passenger_notifications.sql) | SQL script: DDL for the passenger reference table and the `enriched_passenger_notifications` output view |
| [`schemas/passenger-notification.schema.json`](schemas/passenger-notification.schema.json) | JSON Schema for the `PassengerNotification` payload — required so the enrichment pipeline can map the envelope into typed Flink `Row` columns |
| [`enrichment/passengers.csv`](enrichment/passengers.csv) | Global passenger registry (also used for inbound enrichment) |

##### How the pipeline is declared

In [`agents-with-sql-enrichment.json`](agents-with-sql-enrichment.json) the
`PassengerNotification` output carries `schema` and `sqlEnrichment` alongside the existing
`eventType`, `topic`, and `description` fields:

```json
{
  "eventType": "PassengerNotification",
  "topic":     "agent-passenger-notifications",
  "schema":    "samples/airline-agent/schemas/passenger-notification.schema.json",
  "sqlEnrichment": {
    "sqlFile":        "samples/airline-agent/enrichment/enrich_passenger_notifications.sql",
    "inputViewName":  "raw_passenger_notifications",
    "outputViewName": "enriched_passenger_notifications"
  }
}
```

The `schema` field is required — it tells the pipeline how to parse each envelope payload into
a typed Flink `Row` before handing it to the SQL view.

##### Output view contract

The final view `enriched_passenger_notifications` projects the three columns required by the
enrichment pipeline:

| Column | Value |
|---|---|
| `timestamp` | `n.timestamp` (from the notification payload) |
| `entity_id` | `n.passengerNumber` |
| `payload_json` | Full enriched JSON with all contact fields added |

## 6. Running this use case

**From the project root**, after the infrastructure is up (see the
[main README Quick Start](../../README.md#3-quick-start)):

```bash
# 1. Build the project (if not already built)
./build.sh

# 2. Start the infrastructure
./run.sh up

# 3. Deploy this use case (pre-creates the Kafka topics and submits the Flink job)
./samples/airline-agent/scripts/deploy.sh

# 4. Open the dashboard
open http://localhost:3010
```

Select **Transport — Airline Agent** in the use-case selector, then click a scenario button in the
**Send Events** panel.

The job can also be deployed from the dashboard (**Deploy** button on the *Airline Agent* card) or
through the BFF REST API:

```bash
curl -X POST http://localhost:8080/api/agents/airline-agent/start
```

Stop the job with `POST /api/agents/airline-agent/stop`.

By default the job uses [`agents.json`](agents.json), i.e. the CSV-based enrichment. To run the
SQL-based enrichment variant instead (DataStream runtime only, see [§5b](#5b-alternative-sql-based-enrichment)),
pass the alternative descriptor:

```bash
./samples/airline-agent/scripts/deploy.sh kafka:29092 samples/airline-agent/agents-with-sql-enrichment.json
```

#### Running on the PTF runtime

The same sample can run on the **Process Table Function (PTF) runtime** instead of the DataStream
runtime, with the dedicated [`deploy-ptf.sh`](scripts/deploy-ptf.sh) script. It submits
`AgentBasedPTFJob` (job name *Airline Agent (PTF)*) with the same `agents.json`:

```bash
# Deploy on the PTF runtime (instead of step 3 above)
./samples/airline-agent/scripts/deploy-ptf.sh
```

Like `deploy.sh`, it accepts `[bootstrap-servers] [descriptor-path]`. The default `agents.json`
(CSV-based enrichment) is fully supported there. `agents-with-sql-enrichment.json` can also be
submitted, but `sqlEnrichment` is ignored on this runtime (a warning is logged) and the CSV-based
`enrichment` is applied. Other PTF-runtime limits, such as no archive hot reload through
`archiveControlTopic`, are listed in [main README §5.2](../../README.md#52-ptf-implementation). Demo
scenarios have their own script, see [§7](#7-demo-scenarios).

See the [main README Quick Start](../../README.md#3-quick-start) for the infrastructure details and
the [BFF README](../../event-rule-frontend/bff/README.md) for the full REST API.

## 7. Demo scenarios

See [`demo-scenarios.json`](demo-scenarios.json). Click a scenario in the **Send Events** panel to
send its events in order. Each scenario uses its own flight number, so scenarios can be played
independently.

| # | Scenario | Flight | What to observe |
|---|---|---|---|
| 1 | Check-in open event 48 h before flight | `EY082` | `FLIGHTOPEN` registers the `CHECK-IN-OPEN` schedule for 2026-10-13T20:29:16Z. A later `FLIGHTINFO` event moves event time past that point, the schedule fires, and a `CheckInOpen` flight notification plus one passenger notification per passenger are produced |
| 2 | Multiple flight delays | `AF077` | The first `FLIGHTDELAYED` raises a delay notification. Further delays within 30 minutes are not notified again, but the third delay raises the "Burst of Delay Event indicating a potential flight cancellation" `Information` notification |
| 3 | Passenger check-in | `AF099` | `JS` checks in more than 48 h before departure (early check-in rule); `LW` checks in within the 48 h window and is checked in |
| 4 | Meal shortage situation | `AF021` | With 5 meals per class and 5 economy passengers checked in, a `MealShortage` notification is raised. Check-in of a further passenger keeps the situation. A new catering event with 10 meals raises `MealShortageCleared` |

You can also run scenarios from the command line:

```bash
# Run all scenarios
./scripts/launch-demo-scenario.sh airline-agent

# Run a single scenario
./scripts/launch-demo-scenario.sh airline-agent multiple_flight_delay

# Skip the automatic entity-state reset after each scenario
./scripts/launch-demo-scenario.sh airline-agent --no-reset
```

When the job runs on the **PTF runtime** (see [§6](#running-on-the-ptf-runtime)), use the dedicated
script instead. The PTF job has no entity-reset sentinel, so the script cancels the job, moves its
consumer-group offsets to the end of the topics, resubmits it with
[`deploy-ptf.sh`](scripts/deploy-ptf.sh) (empty state) and waits for it to be `RUNNING` before
publishing the events of **each** scenario:

```bash
# Run all scenarios, the PTF job being restarted before each one
./scripts/launch-demo-scenario-ptf.sh airline-agent

# Run a single scenario
./scripts/launch-demo-scenario-ptf.sh airline-agent multiple_flight_delay

# Same thing through the wrapper scoped to this sample (no use-case argument)
./samples/airline-agent/scripts/launch-demo-scenario-ptf.sh multiple_flight_delay
```

Scenario ids: `open-flight-and-checkin-open`, `multiple_flight_delay`, `passenger-checkin`,
`meal-shortage-situation`.

## 8. Updating the decision archive

The rules are authored in Decision Designer. [`di-project/AirlineDecisionService.zip`](di-project/AirlineDecisionService.zip)
contains the decision project sources.

To fetch a new archive version that has been deployed to the embedded deployment space of a DI
runtime, use [`scripts/get-dsa.sh`](scripts/get-dsa.sh). It saves
`AirlineDecisionService_<version>.jar` into this directory:

```bash
export DIADMIN_USER=<user>
export DIADMIN_PASSWORD=<password>

# Optional, defaults shown. Replace with URL of IBM DI CMS installation
export DI_CMS_URL=https://localhost:3000
export DI_TOKEN_URL=https://localhost:18082

./samples/airline-agent/scripts/get-dsa.sh 1.1.0
```

Requires `curl` and `jq`. After downloading a new version, update `ruleset.path` in
[`agents.json`](agents.json) to the new file name. Then either redeploy the job or hot-swap the
archive with [`scripts/broadcast-reload.sh`](../../scripts/README.md) through the archive control
topic `agent-airline-archive-control`.

## 9. Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| No check-in-open notification after `FLIGHTOPEN` | Schedules fire on **event time**, not wall-clock time. Send a later event for the same flight (for example `FLIGHTINFO`, as in scenario 1) so the watermark passes the schedule timepoint. Idle topics only release the watermark after their idleness delay (30 s for the passenger topic, 1 minute by default) |
| Only one notification for several delay events | Expected: the *Flight Delayed Notification Rule* suppresses notifications when a delay was already received in the last 30 minutes |
| Flink job fails at startup with the archive not found | `ruleset.path` in [`agents.json`](agents.json) must match the jar name present in this directory (currently `AirlineDecisionService_1.2.5.jar`) |
| `409` when clicking **Deploy** | The job is already running. Stop it first, then redeploy |
| Meal shortage not detected | Check that the catering counts and the `check-inStatus` / `checkinCounter` values lead to a count above the thresholds described in [Situations — Meal shortage](di-project/docs/situations.md#3-meal-shortage) |
| `FLIGHTOPEN` enrichment missing aircraft or passenger data | Verify the CSV files under `enrichment/` are present and the flight number in the event matches a row in `flights.csv` and `flight_passengers.csv`. Check the Flink TaskManager logs for enrichment warnings (or, with `agents-with-sql-enrichment.json`, for SQL startup errors). |
| `sqlEnrichment` seems ignored | SQL enrichment only runs on the DataStream runtime. With `EVENT_RULE_RUNTIME=ptf` it is ignored (a warning is logged) and the CSV-based `enrichment` is used instead. |
| Scenario re-run gives unexpected results | The flight entity state is kept for 7 months. Use the automatic entity-state reset after each scenario (default of `launch-demo-scenario.sh`, disabled by `--no-reset`) |
| `get-dsa.sh` reports no matching decision | The version must exist in the `embedded` deployment space. The script lists the available decision archives |

For infrastructure-level troubleshooting (Kafka, Flink, dashboard connectivity), see the
[main README Troubleshooting section](../../README.md#15-monitoring-and-troubleshooting).

# Transport — Airline Agent

A stateful, event-driven airline operations pipeline built on the Event Rule Agent pattern. It
shows how Flink and an IBM Decision Intelligence rule archive can manage the events generated by an
airline system: **flight events** (flight open, flight delayed…), **passenger events** (check-in,
cancel check-in…) and **catering events** (meal counts) are correlated per flight and turned into
flight, passenger and catering notifications.

It also demonstrates **scheduling**: when a flight is opened, a rule asks the Agent to wake up
48 hours before departure and notify the passengers that check-in is open.

## 1. Subscriptions and operations

The Agent consumes three Kafka topics plus the internal `Schedule` event. Each event type is routed
to its own Decision Intelligence operation. In every operation the entity (the `Flight`) is passed
in as `flight`, and the matching history is passed in as a `past…Events` list.

| Event type | Topic | Operation | Current event field | History field | Horizon |
|---|---|---|---|---|---|
| `FlightEvent` | `agent-flight-events` | `ProcessFlightEvent` | `flightEvent` | `pastFlightEvents` | time — 96 h |
| `PassengerEvent` | `agent-passenger-events` | `ProcessPassengerEvent` | `passengerEvent` | `pastPassengerEvents` | time — 96 h |
| `CateringEvent` | `agent-catering-events` | `ProcessCateringEvent` | `cateringEvent` | `pastCateringEvents` | hybrid — last 100 events or 96 h |
| `Schedule` | *none (generated by the Agent)* | `ProcessSchedule` | `schedule` | `pastFlightEvents` | — |

Every operation can return:

- `flightNotifications`, `passengerNotifications` and `cateringStatusNotifications` (outbound
  events, depending on the operation — see [`agents.json`](agents.json)),
- `scheduleRequests` (`scheduleRequestsField`), used to register timers.

The `Schedule` subscription has no topic and no horizon: the events are produced by the Agent when a
timer registered through a `ScheduleRequest` fires. See
[§7.4 Scheduling](../../docs/AGENT_PATTERN_DESIGN.md#74-scheduling) for the semantics.

The passenger topic is declared with `"idleness": "30s"` in the top-level `topics` of [`agents.json`](agents.json) so
that a quiet passenger topic does not hold back the event-time watermark and delay schedules.

The ruleset also declares the archive control topic `agent-airline-archive-control`, used for
zero-downtime archive reloads.

See [`../../docs/AGENT_PATTERN_DESIGN.md`](../../docs/AGENT_PATTERN_DESIGN.md) for the generic
rule signature and the full descriptor field reference.

## 2. Event shapes

All timestamps are ISO-8601 UTC strings. Every event must carry the `flightNumber`, which is the
entity key. The full data model is in the BOM of the
[decision project](di-project/AirlineDecisionService.zip).

### Flight event — `agent-flight-events`

| Field | Description |
|---|---|
| `timestamp` | Event time |
| `flightNumber` | Entity key |
| `type` | `FLIGHTOPEN`, `FLIGHTDELAYED`, `FLIGHTCANCELLED`, `FLIGHTCLOSE`, `FLIGHTINFO`, `PASSENGERADDED`, `PASSENGERMODIFIED`, `PASSENGERREMOVED` |
| `flight` | The flight data (see below). `FLIGHTOPEN` carries the full flight; other events only the changed fields (for example `expectedDate` for `FLIGHTDELAYED`) |

The rules currently act on `FLIGHTOPEN` and `FLIGHTDELAYED`. Other types are stored in the event
history and can be used to advance event time.

```json
{
  "timestamp": "2026-10-01T20:29:16Z",
  "flightNumber": "EY082",
  "type": "FLIGHTOPEN",
  "flight": {
    "flightNumber": "EY082",
    "aircraftId": "AF-343-TY",
    "aircraftType": "A380",
    "date": "2026-10-15T20:29:16Z",
    "expectedDate": "2026-10-15T20:29:16Z",
    "origin": "CDG",
    "destination": "LHR",
    "duration": "PT1H",
    "cateringInformation": {
      "economyTotalMealCount": 10,
      "businessTotalMealCount": 10,
      "firstTotalMealCount": 10
    },
    "passengers": [
      {
        "passengerId": "JS",
        "name": "John Smith",
        "birthdate": "1980-10-19T20:29:16Z",
        "citizenship": "USA",
        "residenceCountry": "USA",
        "loyaltyStatus": "Gold",
        "check-inStatus": "Pending",
        "travelClass": "Economy"
      }
    ]
  }
}
```

`Flight` enumerations: `loyaltyStatus` is `Gold`, `Silver` or `Platinum`; `check-inStatus` is
`Pending`, `CheckedIn` or `Cancelled`; `travelClass` is `Economy`, `Business` or `First`. The
optional `checkinCounter` object (`economyCheckinCounter`, `businessCheckinCounter`,
`firstCheckinCounter`) holds the number of checked-in passengers per class.

### Passenger event — `agent-passenger-events`

```json
{
  "timestamp": "2026-10-14T13:30:00Z",
  "flightNumber": "AF099",
  "passengerId": "LW",
  "type": "CHECKIN"
}
```

`type` is `CHECKIN`, `CANCELCHECKIN` or `NOSHOW`. `passengerId` must match a passenger of the
flight.

### Catering event — `agent-catering-events`

```json
{
  "timestamp": "2026-10-13T13:30:00Z",
  "flightNumber": "AF021",
  "cateringInformation": {
    "economyTotalMealCount": 5,
    "businessTotalMealCount": 5,
    "firstTotalMealCount": 5
  }
}
```

### Schedule event (internal)

Produced by the Agent when a `ScheduleRequest` fires. It is never sent to Kafka.

| Field | Description |
|---|---|
| `timestamp` | The timer timestamp |
| `id` | `id` of the `ScheduleRequest` that fired (for example `CHECK-IN-OPEN`) |
| `description` | `description` of the `ScheduleRequest` |

## 3. Output topics

| Event type | Topic | When |
|---|---|---|
| `FlightNotification` | `agent-flight-notifications` | A flight-level notification is raised (delay, possible cancellation, check-in open, meal shortage…) |
| `PassengerNotification` | `agent-passenger-notifications` | A notification addressed to one passenger (for example check-in open) |
| `CateringStatusNotification` | `agent-catering-status-notifications` | Declared in `agents.json`. The current archive data model does not produce this event type yet |
| `entity-changelog` | `agent-flight-entity-changelog` | Flight entity state updated (side-output, every cycle) |
| `agent-error` | `agent-airline-errors` | Rule engine or processing errors |

The top-level `topics` and `outboundTopics` of `agents.json` expose the flight notification, passenger notification, error and changelog
topics in the dashboard. The catering status topic is created on deployment but is not displayed.

### Flight notification output shape

| Field | Description |
|---|---|
| `timestamp` | Time the notification was raised |
| `flightNumber` | Flight concerned |
| `type` | `Cancelled`, `CheckInOpen`, `Closed`, `Delayed`, `Information`, `MealShortage`, `MealShortageCleared` |
| `message` | Human-readable text |

```json
{
  "timestamp": "2026-10-15T13:50:00Z",
  "flightNumber": "AF077",
  "type": "Information",
  "message": "Burst of Delay Event indicating a potential flight cancellation"
}
```

### Passenger notification output shape

| Field | Description |
|---|---|
| `timestamp` | Time the notification was raised |
| `flightNumber` | Flight concerned |
| `passengerNumber` | `passengerId` of the addressee |
| `message` | Human-readable text |

```json
{
  "timestamp": "2026-10-13T20:29:16Z",
  "flightNumber": "EY082",
  "passengerNumber": "JS",
  "message": "Checking for Flight: EY082 is open. Please check-in online"
}
```

### Entity changelog

When `stateConfig.changeLogTopic` is set (this agent uses `agent-flight-entity-changelog`), a
side-output record is emitted to that topic whenever the rule engine returns an updated `Flight`
entity. Each record has the form:

```json
{
  "entityId":   "AF021",
  "entityType": "Flight",
  "timestamp":  1750000000000,
  "entity":     { "flightNumber": "AF021", "shortMealSituation": true, ["..."] }
}
```

## 4. Decision rules

All rules live in the Decision Intelligence archive (`AirlineDecisionService`). The decision project
is organized in one rule project per operation, plus a shared data model (`AirlineDataModel`).

| Rule project (operation) | Rule package | Rule | Purpose |
|---|---|---|---|
| Process Flight Event | Flight State Maintenance Rules | Flight Initialization Rule | On `FLIGHTOPEN`, store the validated flight and schedule the `CHECK-IN-OPEN` callback 48 h before departure |
| | | Flight Delayed Rule | On `FLIGHTDELAYED`, store the new expected date on the flight |
| | Flight Event Processing Rules | Flight Delayed Notification Rule | Notify of a delay, at most once per 30 minutes |
| | | Detect Flight Possible Cancellation | Notify when a burst of delay events suggests a cancellation |
| Process Schedule Event | Schedule Processing Rules | Check-In Open Rule | On `CHECK-IN-OPEN`, raise a flight notification |
| | | Check-In Open Notify Passengers | On `CHECK-IN-OPEN`, notify every passenger of the flight |
| Process Passenger Event | Initialization Rules | Find Passenger | Locate the passenger of the event in the flight |
| | Passenger Event Processing Rules | Passenger Check-In | Check in the passenger if check-in is open (less than 48 h before departure) |
| | | Early Passenger Check-In | Handle a check-in received more than 48 h before departure |
| | | Passenger Cancel Check-In | Cancel the passenger check-in |
| | Situation Detection Rules | Detect Meal Shortage Situation | Raise a `MealShortage` notification |
| | | Meal Shortage Situation Cleared | Raise a `MealShortageCleared` notification |
| Process Catering Event | Catering Event Rules | Save Catering Information | Store the received meal counts on the flight |
| | Situation Detection | Detect Short Meal Situation | Raise a `MealShortage` notification |
| | | Short Meal Situation Cleared | Raise a `MealShortageCleared` notification |

### Meal shortage computation

The catering situation of a flight is *good* unless one class is over its threshold, comparing the
number of checked-in passengers to the number of meals loaded:

| Class | Shortage when checked-in passengers exceed |
|---|---|
| Economy | 95 % of the economy meals |
| Business | 90 % of the business meals |
| First | 85 % of the first-class meals |

The flight keeps a `shortMealSituation` flag with start and end dates, so a notification is raised
only when the situation changes, whether it is triggered by a passenger event (check-in or cancel
check-in) or by a catering event (new meal counts).

### Rule examples

```
// Flight Initialization Rule
if
    the type of 'the flight event' is FLIGHT OPEN
then
    // initialize the entity
    set the flight of 'the result' to the validated flight from the flight of 'the flight event' ;

    // post a schedule to trigger a check-in open event 48h before departure
    add a new Schedule Request where
        the id is "CHECK-IN-OPEN" ,
        the status is "START",
        the description is "Trigger check-in open event 48h before flight" ,
        the timepoint is the date of the flight of 'the flight event' - 48 hours
    to the schedule requests of 'the result' ;
```

```
// Flight Delayed Notification Rule
if
    the type of 'the flight event' is FLIGHT DELAYED
  and
    // avoid sending too much notifications
    there is no Flight Event in 'the past flight events'
        where the type of this Flight Event is FLIGHT DELAYED
        and this Flight Event is within 30 minutes before now ,
then
    add a new Flight Notification where
        the flight number is the flight number of 'the flight event' ,
        the timestamp is now ,
        the message is `Flight as being delayed. new expected time: { the expected date of the flight of 'the flight event' }` to the flight notifications of 'the result' ;
```

```
// Detect Flight Possible Cancellation
if
    the type of 'the flight event' is FLIGHT DELAYED
  and
    there are at least 2 Flight Events in 'the past flight events' during the period of 30 minutes before now where the type is FLIGHT DELAYED,
then
    define 'the notification' as a new Flight Notification where
        the timestamp is now ,
        the type is Information ,
        the message is "Burst of Delay Event indicating a potential flight cancellation" ,
        the flight number is the flight number of 'the flight' ;
    add 'the notification' to the flight notifications of 'the result';
```

```
// Detect Short Meal Situation (catering events)
if
    'the flight' is not in short meal situation
    and it is not true that the catering situation for 'the flight' is good
then
    'the flight' gets short meal situation ;
    set the short meal situation start date of 'the flight' to now;
    define 'the notification' as a new Flight Notification where
      the timestamp is now ,
      the type is Meal Shortage ,
      the message is `Meal shortage situation. Available meals: {the report of the catering information of 'the flight'}, Passenger information: {the passenger information of 'the flight' }` ,
      the flight number is the flight number of 'the flight';
    add 'the notification' to the flight notifications of 'the result' ;
```

```
// Short Meal Situation Cleared (catering events)
if
    'the flight' is in short meal situation
    and the catering situation for 'the flight' is good
then
    'the flight' does not get short meal situation ;
    set the short meal situation end date of 'the flight' to now;
    define 'the notification' as a new Flight Notification where
      the timestamp is now ,
      the type is Meal Shortage Cleared ,
      the message is "Meal shortage situation is cleared" ,
      the flight number is the flight number of 'the flight';
    add 'the notification' to the flight notifications of 'the result' ;
```

```
// Check-In Open Notify Passengers
for each Passenger called 'the passenger' , in the passengers of 'the flight'
if
    the id of 'the schedule' is "CHECK-IN-OPEN"
then
    define 'the notification' as a new Passenger Notification where
      the timestamp is now ,
      the passenger number is the passenger id of 'the passenger' ,
      the flight number is the flight number of 'the flight' ,
      the message is `Checking for Flight: { the flight number of 'the flight'} is open. Please check-in online` ;
    add 'the notification' to the passenger notifications of 'the result';
```

## 5. Running this use case

**From the project root**, after the infrastructure is up (see the
[main README Quick Start](../../README.md#3-quick-start)):

```bash
# 1. Build the project (if not already built)
./build.sh

# 2. Start the infrastructure
./run.sh up

# 3. Deploy this use case (pre-creates the Kafka topics and submits the Flink job)
./samples/airline-agent/scripts/deploy.sh

# 4. Open the dashboard
open http://localhost:3010
```

Select **Transport — Airline Agent** in the use-case selector, then click a scenario button in the
**Send Events** panel.

The job can also be deployed from the dashboard (**Deploy** button on the *Airline Agent* card) or
through the BFF REST API:

```bash
curl -X POST http://localhost:8080/api/agents/airline-agent/start
```

Stop the job with `POST /api/agents/airline-agent/stop`.

See the [main README Quick Start](../../README.md#3-quick-start) for the infrastructure details and
the [BFF README](../../event-rule-frontend/bff/README.md) for the full REST API.

## 6. Demo scenarios

See [`demo-scenarios.json`](demo-scenarios.json). Click a scenario in the **Send Events** panel to
send its events in order. Each scenario uses its own flight number, so scenarios can be played
independently.

| # | Scenario | Flight | What to observe |
|---|---|---|---|
| 1 | Check-in open event 48 h before flight | `EY082` | `FLIGHTOPEN` registers the `CHECK-IN-OPEN` schedule for 2026-10-13T20:29:16Z. A later `FLIGHTINFO` event moves event time past that point, the schedule fires, and a `CheckInOpen` flight notification plus one passenger notification per passenger are produced |
| 2 | Multiple flight delays | `AF077` | The first `FLIGHTDELAYED` raises a delay notification. Further delays within 30 minutes are not notified again, but the third delay raises the "Burst of Delay Event indicating a potential flight cancellation" `Information` notification |
| 3 | Passenger check-in | `AF099` | `JS` checks in more than 48 h before departure (early check-in rule); `LW` checks in within the 48 h window and is checked in |
| 4 | Short meal situation | `AF021` | With 5 meals per class and 5 economy passengers checked in, a `MealShortage` notification is raised. Check-in of a further passenger keeps the situation. A new catering event with 10 meals raises `MealShortageCleared` |

You can also run scenarios from the command line:

```bash
# Run all scenarios
./scripts/launch-demo-scenario.sh airline-agent

# Run a single scenario
./scripts/launch-demo-scenario.sh airline-agent multiple_flight_delay

# Skip the automatic entity-state reset after each scenario
./scripts/launch-demo-scenario.sh airline-agent --no-reset
```

Scenario ids: `open-flight-and-checkin-open`, `multiple_flight_delay`, `passenger-checkin`,
`short-meal-situation`.

## 7. Updating the decision archive

The rules are authored in Decision Designer. [`di-project/AirlineDecisionService.zip`](di-project/AirlineDecisionService.zip)
contains the decision project sources.

To fetch a new archive version that has been deployed to the embedded deployment space of a DI
runtime, use [`scripts/get-dsa.sh`](scripts/get-dsa.sh). It saves
`AirlineDecisionService_<version>.jar` into this directory:

```bash
export RTSADMIN_USER=<user>
export RTSADMIN_PASSWORD=<password>

# Optional, defaults shown
export DI_CMS_URL=https://localhost:3000
export DI_TOKEN_URL=https://localhost:18082

./samples/airline-agent/scripts/get-dsa.sh 1.1.0
```

Requires `curl` and `jq`. After downloading a new version, update `ruleset.path` in
[`agents.json`](agents.json) to the new file name. Then either redeploy the job or hot-swap the
archive with [`scripts/broadcast-reload.sh`](../../scripts/README.md) through the archive control
topic `agent-airline-archive-control`.

## 8. Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| No check-in-open notification after `FLIGHTOPEN` | Schedules fire on **event time**, not wall-clock time. Send a later event for the same flight (for example `FLIGHTINFO`, as in scenario 1) so the watermark passes the schedule timepoint. Idle topics only release the watermark after their idleness delay (30 s for the passenger topic, 1 minute by default) |
| Only one notification for several delay events | Expected: the *Flight Delayed Notification Rule* suppresses notifications when a delay was already received in the last 30 minutes |
| Flink job fails at startup with the archive not found | `ruleset.path` in [`agents.json`](agents.json) must match the jar name present in this directory (currently `AirlineDecisionService_1.1.0.jar`) |
| `409` when clicking **Deploy** | The job is already running. Stop it first, then redeploy |
| Meal shortage not detected | Check that the catering counts and the `check-inStatus` / `checkinCounter` values lead to a count above the thresholds in [§4](#meal-shortage-computation) |
| Scenario re-run gives unexpected results | The flight entity state is kept for 7 months. Use the automatic entity-state reset after each scenario (default of `launch-demo-scenario.sh`, disabled by `--no-reset`) |
| `get-dsa.sh` reports no matching decision | The version must exist in the embedded deployment space. The script lists the available decision archives |

For infrastructure-level troubleshooting (Kafka, Flink, dashboard connectivity), see the
[main README Troubleshooting section](../../README.md#14-monitoring-and-troubleshooting).
